Exercise B: Add a New Transmission Interconnector

Connect Bangladesh and Myanmar by adding a cross-border TRN technology to the profile's scenario workbook — then run the model and verify.

1 What You Will Do Exercise B

Goal

Add a new BGD↔MMR interconnector (TRNBGDXXMMRXX) by editing the profile's scenario workbook, registering it in two profile config files, then run the model and verify the technology was created.

Myanmar (MMR) is already in the model as a country, but there is no electricity interconnector linking it to any neighbour. Without one, the solver treats Myanmar as an isolated system: it cannot import or export power, even if trade would be cheaper. In this exercise you add the corridor Bangladesh ↔ Myanmar so the solver can optimise cross-border flows between them.

Analogy

Think of it like wiring a new cable between two buildings. The electrical infrastructure exists at both ends — switchboards, meters, circuits — you are just connecting them so power can flow between the two.

2 The Naming Convention

Every cross-border interconnector follows a strict 13-character format:

TRNprefix
BGDXXfrom (5 chars)
MMRXXto (5 chars)

Each node is encoded as a 3-letter ISO country code + 2-character sub-region. Countries without sub-regions use XX. For example, Bangladesh is BGDXX (BGD + XX), Myanmar is MMRXX (MMR + XX), and India East is INDEA (IND + EA).

Your new technology code: TRNBGDXXMMRXX

Tip

The "from" node is always alphabetically first. BGD comes before MMR, so the code is TRNBGDXXMMRXX, not TRNMMRXXBGDXX. This is a convention, not a direction: the technology can carry power both ways.

    What do these mean?

    • CapacityToActivityUnit = 31.536 — converts GW to PJ/year (1 GW running 24/7 for a year = 31.536 PJ). Same for all technologies.
    • InputActivityRatio = 1 — for every PJ of electricity that enters the line, the model consumes 1 PJ from the source node's dispatch bus.
    • OutputActivityRatio = 0.96 — 4% is lost in transmission, so the destination receives 0.96 PJ per PJ consumed. This matches the TransmissionLossFactor of 0.04 from the Interconnector_Params sheet.
    Consistency check

    OutputActivityRatio should equal 1 - TransmissionLossFactor. If you set TransmissionLossFactor = 0.04, then OutputActivityRatio = 0.96. The existing BGD-INDEA uses 0.035 loss / 0.95 output (note: 0.95 instead of 0.965 because OSeMOSYS Global used a different convention; for new corridors, keep them consistent).

4 Register in technology_types.csv

Open examples/unescap/config/scenarios/technology_types.csv in a text editor or spreadsheet. Find the INTERCONNECTORS section and add one row:

INTERCONNECTORS,TRNBGDXXMMRXX

This tells the scenario-stage rules (relax_interconnectors, set_interconnector_direction, and the cap-to-residual rule) that TRNBGDXXMMRXX is a cross-border interconnector. Without this registration, those rules ignore it.

Important

If you also want to add the MMR internal transmission technologies (PWRTRNMMRXX, RNWTRNMMRXX, etc.), the transmission stage creates them automatically when MMR is in the countries: list in examples/unescap/config/preparation/Config_country_codes.yaml. You do not need to add them manually — Exercise A already put MMR there.

5 Register in AO Extensions

When you add a brand-new technology to the scenario workbook, the scenario stage needs to know it should create rows for it in the A-O workbooks. This is controlled by the extension decision list, examples/unescap/config/scenarios/ao_extension_decisions.csv.

Why this file?

Remember from Session 2: A1/A2 ran once and are frozen in the BAU snapshot. The A-O workbooks were built before your new interconnector existed. The extension decision list tells the scenario stage to inject the new technology rows into the A-O workbooks during processing — without it, the stage would not know about the technology even though the scenario workbook has all the data.

Open examples/unescap/config/scenarios/ao_extension_decisions.csv and add a new row. The CSV carries the five decision columns you actually fill in — AO_Code_To_Add, Include, Override_Template_AO, Override_Tech.Name_AO, Notes. The wider table below shows the full set of columns the stage derives, so you can see where your decision lands:

Key columns explained

Only five of these columns are yours to set; the rest are derived. In ao_extension_decisions.csv you write AO_Code_To_Add = TRNBGDXXMMRXX and Include = Y, and leave Override_Template_AO and Override_Tech.Name_AO empty. Empty overrides mean the stage clones the row structure from the existing BGD–INDEA interconnector and generates the technology name (“Myanmar, region XX”) itself. Fill an override in only when you disagree with what it picked, and say why in Notes.

Only for new techs

You only need this step when adding a technology that did not exist before in the A-O workbooks. If you were modifying an existing interconnector’s parameters (changing costs, capacity, etc.), editing the scenario workbook alone would be enough — the scenario stage overwrites those values during materialisation.

5b. Make sure both regions are known

Region codes are turned into human-readable names (“Bangladesh, region XX”) for the A-O workbook columns. The names come from the country authority you edited in Exercise A, examples/unescap/config/preparation/Config_country_codes.yaml, so there is no source file to patch here.

Check that both endpoints of your new interconnector are declared. BGDXX comes from the BGD entry that is already in country_data; MMRXX comes from the MMR entry Exercise A added:

country_data:
  MMR:
    english_name: "Myanmar"
    ostram_name: "Myanmar"

This profile declares only the two countries it models, BGD and IND, plus whatever you add. If a region code is missing when you run the profile, preparation stops and names the code — it does not guess a name or fall back to the project-root country list.

When can you skip this?

If both endpoints of your interconnector are already declared in country_data (e.g. adding a second BGD↔IND corridor), you do not need to touch this file. You only need this step when connecting to a country the profile has never modelled.

6 Configure Scenario YAMLs

Each scenario has its own config files under examples/unescap/config/scenarios/<scenario>/. Three scenarios use interconnector rules; BAU does not (it has no relax_interconnectors.yaml).

6a. Capacity limits — relax_interconnectors.yaml

This file controls how much capacity the solver can build for each interconnector. Each entry under overrides: is a year–GW map that caps annual investment. An empty map {} means “freeze at residual capacity” (no new investment). You need to add TRNBGDXXMMRXX to three scenarios.

Where do the values come from?

Look at the existing TRNBGDXXINDEA entry as your guide. Its values (2023: 2.50, 2028: 6.50, … 2033: 8.50) come from the real project pipeline — the commissioned and planned HVDC capacities from the Interconnectors sheet. For our exercise interconnector, the only project is a single 0.5 GW link commissioning in 2030. We set {2029: 0, 2030: 0.5} — the explicit zero before COD prevents the interpolation logic from allowing investment in earlier years.

A_Calibrated_BAU — open config/scenarios/A_Calibrated_BAU/relax_interconnectors.yaml. The file currently has:

overrides:
  TRNBGDXXINDEA: {2023: 2.50, 2028: 6.50, 2029: 7.00, 2030: 7.75, 2033: 8.50}

Add the new line below TRNBGDXXINDEA:

  TRNBGDXXMMRXX: {2029: 0, 2030: 0.5}   # new: 500 MW project, COD 2030

B_Optimised_VRE — open config/scenarios/B_Optimised_VRE/relax_interconnectors.yaml. Same structure as A — add the same line below TRNBGDXXINDEA:

  TRNBGDXXMMRXX: {2029: 0, 2030: 0.5}   # new: 500 MW project, COD 2030

C_Target_VRE — open config/scenarios/C_Target_VRE/relax_interconnectors.yaml. Same — add the line:

  TRNBGDXXMMRXX: {2029: 0, 2030: 0.5}   # new: 500 MW project, COD 2030
What about BAU?

The BAU scenario does not have a relax_interconnectors.yaml — it does not run the relax rule. Instead, the cap-to-residual rule freezes every TRN at its residual capacity automatically. Your new interconnector will be capped at 0 GW before 2030 and 0.5 GW from 2030 — no config needed.

6b. Flow direction — set_interconnector_direction.yaml

This file only exists in B_Optimised_VRE (it is used in Exercise 3 of the main guide). A_Calibrated_BAU and C_Target_VRE do not have this file, so their interconnectors are always bidirectional.

The B_Optimised_VRE file currently says directions: {}, which means all interconnectors are bidirectional. For this exercise, leave it unchanged — the new BGD↔MMR link will be bidirectional by default.

# config/scenarios/B_Optimised_VRE/set_interconnector_direction.yaml
# No changes needed — {} = bidirectional for all links
directions: {}
Tip

To experiment with direction control (forward-only, reverse-only), see Exercise 3.5: Control the Direction in the main training guide.

7 Run the Model

Not runnable from this branch yet

This branch carries the UNESCAP example assets only. The example and --profile commands below arrive with the parallel profile-engine branch. Until that branch is merged, work through the edits and read the commands as the interface you will use.

The commands are the same on Windows, macOS, and Linux, and they do not depend on which directory you are in — the profile is named, not located.

  1. Prepare the profile (once)

    The profile ships input CSVs and a scenario workbook, not a built model. Preparation turns them into the base model. You only repeat this after changing country membership.

    python -m ostram example prepare unescap
  2. Run scenarios A and B 
    python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU,B_Optimised_VRE"
  3. Run scenario C

    C needs solved A_Calibrated_BAU results to calculate its targets. That dependency is declared in config/scenarios/registry.json, so running C before A stops with a clear message instead of producing quiet nonsense.

    python -m ostram --profile unescap run --scenarios "C_Target_VRE"
  4. Collect the results

    Each run writes into its own workspace folder, so nothing is overwritten and there is nothing to copy by hand.

    python -m ostram example report unescap
Tip

You do not need to re-prepare the profile. The scenario stage reads the scenario workbook fresh on every run and detects the new technology automatically.

Impact on BAU

Since the new rows are tagged scenario = BAU, all scenarios see this interconnector. Check your BAU results after running: if NewCapacity for TRNBGDXXMMRXX is unexpectedly large, add a TotalAnnualMaxCapacityInvestment restriction in the scenario workbook's Restrictions sheet (or set TotalAnnualMaxCapacity = ResidualCapacity in Interconnector_Params for BAU to freeze it).

8 Verify

After running, open the A-O workbook for one of the scenarios you ran (not BAU — BAU uses the frozen A1/A2 snapshot and does not process extensions):

<workspace>/preparation/A1_Outputs/A1_Outputs_A_Calibrated_BAU/A-O_Parametrization.xlsx

Go to the Secondary Techs sheet and search for TRNBGDXXMMRXX. You should see rows for CapitalCost, FixedCost, ResidualCapacity, and other parameters. Verify that:

  • The Tech.Name says “Myanmar”, not “India” (if it says India, check that REGION_NAME_MAP has MMRXX from Step 5b and that Suggested_Tech.Name_AO is blank in the Extensions file).
  • CapitalCost = 450 (not 292 — 292 is the INDEA template value; 450 is what you entered in the scenario workbook).
  • ResidualCapacity = 0 before 2030, 0.5 from 2030 onward.
Why not check BAU?

The A1_Outputs_BAU/ folder holds the original A1/A2 snapshot — it was created before your interconnector existed. Only the scenario-specific folders (A1_Outputs_A_Calibrated_BAU/, A1_Outputs_B_Optimised_VRE/) are processed by the scenario stage and contain the new technology. Everything under the workspace is generated; none of it belongs in the profile.

Troubleshooting checklist

  • The Tech column in the scenario workbook is exactly TRNBGDXXMMRXX (13 characters, no spaces, no trailing whitespace).
  • The scenario column says BAU (not “bau” or “Bau”) — this is the workbook's base scenario, not where you check the output.
  • You saved OSTRAM_Scenario_Inputs.xlsx before running the pipeline.
  • MMR is in country_data in config/preparation/Config_country_codes.yaml.
  • TRNBGDXXMMRXX has Include = Y in config/scenarios/ao_extension_decisions.csv.
  • Override_Tech.Name_AO is blank — if you fill it with the template name (“India, region EA”), the stage uses it literally instead of generating the correct Myanmar name.
Tip

If you see INDEA values (CapitalCost 292, name mentioning “India”), check that Override_Tech.Name_AO is blank in ao_extension_decisions.csv and that MMR is declared in Config_country_codes.yaml. Then run again — each run gets a fresh workspace folder, so there is nothing to delete by hand.

How OSTRAM Aggregates Interconnectors

Key concept

OSTRAM represents all physical interconnectors between two nodes as a single TRN technology with two operation modes (forward and reverse). The Interconnectors sheet documents the individual projects for traceability, but in the model they are summed into one technology with shared capacity. The solver decides how much power flows in each direction per timeslice.

For controlling the direction of flow (forward-only, reverse-only, or bidirectional), see Exercise 3.5: Control the Direction in the main training guide, and the measured comparison in interconnector direction results.

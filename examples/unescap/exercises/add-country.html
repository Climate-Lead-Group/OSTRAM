Exercise A: Add a New Country to the Model

Add Myanmar (MMR) to your OSTRAM model as an isolated country — configure, generate, merge, validate, and run the pipeline.

1 What You Will Do Exercise A

Goal

Add Myanmar as a new country to the UNESCAP training profile with the profile-aware country commands. The process clones data from an existing reference country (Bangladesh), generates CSV input files, and merges them into the profile's inputs.

This process is designed for countries that are NOT already in OSeMOSYS Global. The template generator clones a reference country’s data as a starting point. After merging, you can replace the cloned values with real data from IRENA, national energy statistics, or IEA.

Analogy

Think of it like opening a new branch of a business. You copy the processes and pricing from an existing branch as a starting point, then adjust everything to reflect local conditions.

Important

This process resets any prior parametrization for the country — it is designed as a PRE-parametrization step using OSeMOSYS Global defaults.

Profile files vs workspace files

This exercise touches two places. Config files (YAMLs, technology_types.csv) are edited directly in examples/unescap/. Mutable data files (scenario workbook, timeslice workbook, input CSVs) are copied by example prepare and edited in the workspace. An examples/unescap/ path means the profile; “prepared workspace copy” means the workspace.

2 Prerequisites

Before starting, make sure you have the following:

  • The model must already have at least one country configured (BGD and INDEA are already in the model).
  • You need the country’s geographic coordinates (latitude/longitude) for the centerpoint.
  • You need to know which existing country to use as reference — choose one with a similar energy profile.
  • Interconnections are not needed for this exercise — we add the country as an isolated system first (see Exercise B for interconnectors).

Configure profile.yaml for the dashboard

Before preparing the workspace, the new country’s metadata must be present in examples/unescap/profile.yaml. The dashboard reads this file to know which countries, interconnectors, and storage technologies to display. Editing profile.yaml after example prepare invalidates the workspace manifest — so any change must be made now.

Add the metadata yourself

The shipped examples/unescap/profile.yaml does not include Myanmar yet — add the blocks below exactly as shown. While you are in the file, confirm the timeslice_workbook authority has mutable: true, which is what lets Step 2 clone the new timeslice sheets in the workspace.

country_regions — must list the new country:

country_regions:
  - region: BGDXX
    label: Bangladesh
  - region: INDEA
    label: India East
  - region: MMRXX
    label: Myanmar

interconnectors — must list the corridor you will parametrize in Exercise B:

interconnectors:
  - technology: TRNBGDXXINDEA
  - technology: TRNBGDXXMMRXX

storage — must list the long-duration and short-duration storage codes:

storage:
  - LDSBGDXX01
  - LDSINDEA01
  - LDSMMRXX01
  - SDSBGDXX01
  - SDSINDEA01
  - SDSMMRXX01

description — must mention Myanmar:

description: >-
  Bangladesh (BGDXX), India East (INDEA), and Myanmar (MMRXX),
  joined by TRNBGDXXINDEA and TRNBGDXXMMRXX,
  over 2023-2050 in twenty timeslices.

Rename any existing workspace

If you already have a workspace/profiles/unescap folder from a previous run, rename it before preparing a fresh one:

Windows:

ren workspace\profiles\unescap unescap_old

macOS / Linux:

mv workspace/profiles/unescap workspace/profiles/unescap_old
First time?

If there is no existing folder, skip this step — example prepare will create it.

Prepare the workspace

Now start from a guarded clean profile workspace. This removes only ignored generated state and republishes the committed profile authorities:

python -m ostram example prepare unescap --reset
Do this before generating

Do not reset again after Step 5: the country merge deliberately lives in the prepared workspace and a later reset would discard it.

3 Step 1 — Configure the YAML

Open examples/unescap/config/preparation/Config_country_codes.yaml and go to the section marked # ACTIVE CONFIGURATION.

This section contains three commented examples that illustrate different use cases:

  • Single country — one country, one region (the simplest case)
  • Multiple countries — adding several countries at once
  • Country with multiple regions — like India, which is split into sub-regions (INDEA, INDNE, etc.)

The profile ships with exactly this MMR configuration already active, so you can read it as the worked answer. If you have changed it, restore it to:

template_generation:
  - new_country: MMR
    reference_country: BGD
    region: XX
    centerpoint_lat: 19.811800
    centerpoint_lon: 96.602200
    interconnections: []
    demand_scale: 0.18

Field explanations

FieldValueExplanation
new_countryMMR3-letter ISO code for Myanmar
reference_countryBGDExisting country to clone data from (Bangladesh — chosen for similar energy profile in South Asia)
regionXXXX for single-region country (no sub-regions)
centerpoint_lat19.811800Latitude of Myanmar’s geographic center
centerpoint_lon96.602200Longitude of Myanmar’s geographic center
interconnections[] (empty)No interconnections for now — we add the country first as an isolated system. Interconnectors are added separately in Exercise B
demand_scale0.18Critical. Multiplies the cloned SpecifiedAnnualDemand so Myanmar starts from a demand of its own size (~90 PJ in 2023) instead of inheriting Bangladesh’s (~500 PJ). Without it two things go wrong: the unservable gap is covered by the backstop at penalty prices (System cost in the billions), and Myanmar becomes a perfect twin of Bangladesh — that symmetry makes the solver grind for hours instead of minutes. Demand profiles (fractions per timeslice) are never scaled. During Step 2 the generator prints SpecifiedAnnualDemand: cloned values scaled by 0.18 — verify that line appears. For a different country of your own, set it to real annual demand of the new country ÷ reference country’s demand, or omit the field entirely to clone unchanged (default 1.0). This field only acts during template generation for the new country — it never touches the reference country or any existing data.
Tip

The examples in the YAML show advanced cases — multiple countries at once, and countries with multiple regions (like India). For this exercise, we use the simplest case: one country, one region.

4 Step 2 — Run the Template Generator

The commands are identical on Windows, macOS, and Linux, and none of them depend on your current directory — you name the profile, you do not navigate to it.

  1. Generate the country template 
    python -m ostram --profile unescap country template

The command reads the profile's Config_country_codes.yaml, clones data from the reference country (Bangladesh), and writes the generated CSVs into the workspace under <workspace>/preparation/country_templates/MMR/. Nothing under the profile is touched yet.

Expected output:

Profile: unescap
Processing MMR...
  Reference country: BGD
  Region: XX
  Centerpoint: 19.8118, 96.6022
  Interconnections: (none)
  Generating CSV files...
  SpecifiedAnnualDemand: cloned values scaled by 0.18 (28 rows)
  Demand scale: SpecifiedAnnualDemand x 0.18 (vs BGD clone)
  Done.

=== NEXT STEPS ===
1. Review the generated CSVs in <workspace>/preparation/country_templates/MMR/
2. Update Config_country_codes.yaml (country_data, countries, implausible_combinations)
3. Merge:    python -m ostram --profile unescap country merge MMR
4. Validate: python -m ostram --profile unescap country validate MMR
Tip

The command does NOT modify any profile file — it writes new ones into the workspace. Your existing model data is safe.

Verify the timeslice sheets were cloned

The command also clones BGD_CF → MMR_CF and BGD_Dem → MMR_Dem in the workspace copy of the timeslice workbook: <workspace>/profiles/unescap/authorities/timeslice_workbook/OSTRAM_Timeslice_Inputs.xlsx. Open it and confirm both sheets exist — without them the scenario stage stops with an error naming the missing sheet.

5 Step 3 — Review the Generated CSVs

Open <workspace>/preparation/country_templates/MMR/. The folder contains CSV files for all parameters:

  • CapitalCost.csv
  • FixedCost.csv
  • VariableCost.csv
  • ResidualCapacity.csv
  • SpecifiedAnnualDemand.csv
  • And many more…

All values are cloned from Bangladesh — they are starting points, NOT final values. For a real project, you would replace these with actual data from IRENA, national energy statistics, or IEA databases.

Key files to focus on

For a real project, prioritise replacing these files with actual data: ResidualCapacity (installed capacity), CapitalCost / FixedCost / VariableCost (generation costs), SpecifiedAnnualDemand (electricity demand), and fuel availability parameters.

For this training exercise, you can proceed with the cloned values as-is for now. However, note that the OSeMOSYS Global CSVs may not contain ResidualCapacity data for every technology. For example, Bangladesh’s CSVs only carry residual capacity for coal, hydro, oil, and solar PV — technologies like wind, biomass, and nuclear have their capacity defined later in the scenario workbook (Step 10). The template generator can only clone what exists in the CSVs.

CSV coverage gap

If a technology has no ResidualCapacity in the CSV, the cloned country will also lack it. The scenario pipeline’s capacity investment rule (Stage 1b) blocks any technology that has neither residual capacity nor minimum capacity investment — so those technologies will be completely unavailable until you add values in the scenario workbook. Step 10 below covers this calibration.

6 Step 4 — Register Myanmar in the YAMLs

This step registers Myanmar in the rest of examples/unescap/config/preparation/Config_country_codes.yaml so the rest of the pipeline recognises it. There are three sections in the same file. The shipped file only lists BGD and IND — add the MMR entries yourself, exactly as shown below. These are the same sections you would edit for any country of your own.

4a. Add MMR to country_data

Find the country_data section and add the MMR entry:

country_data:
  BGD:
    english_name: "Bangladesh"
    ostram_name: "Bangladesh"
  # ... existing entries ...
  MMR:
    english_name: "Myanmar"
    ostram_name: "Myanmar"

4b. Add MMR to the countries list

Find the countries list and add MMR:

countries:
  - "BGD"
  - "INDEA"
  - "MMR"

4c. Add MMR to implausible_combinations

Find implausible_combinations and add MMR to the relevant technology exclusion lists. These tell the model which technologies are not available in Myanmar. Watch the punctuation if you re-type them: every separator inside the brackets must be a comma (a stray period, e.g. [BGD, IND. MMR], silently corrupts the list):

implausible_combinations:
  CSP: [BGD, MMR]             # no concentrated solar potential
  GAS: [BGD, IND, MMR]        # no PWRGAS technology
  GEO: [BGD, IND, MMR]        # no geothermal resources
  NGS: [BGD, MMR]             # no CCG/OCG/NGS power data
  WAV: [BGD, IND, MMR]        # no wave energy data in model
Warning

MMR must be present in ALL FOUR sections (country_data, countries, implausible_combinations, and technology_types.csv). This profile declares its own country authority and does not fall back to the project-root list, so a missing entry fails loudly rather than being silently filled in from elsewhere.

4d. Add the MMR rows to technology_types.csv

Open examples/unescap/config/scenarios/technology_types.csv in a text editor or spreadsheet. This file maps every technology to its category (GENERATION, STORAGE, TRANSMISSION, etc.) — the scenario rules use it to decide which rules apply to each technology. Every MMR technology that corresponds to a BGD entry must have its own row, in the same category as its BGD counterpart.

How to build this list for a different country

Mirror the existing BGD entries: for each *BGDXX row add the equivalent *MMRXX row in the same category, and for each 9-character MINxxxBGD row add MINxxxMMR. Use only category names that already exist in the file — do not invent new ones. The template generator created all these technologies in the CSVs; this file tells the scenario rules how to classify them.

What happens if you skip this

The scenario rules (add_max_cap_investment_lid_rule, set_retirement_schedule, set_min_capacity_floors, set_vre_targets) use this file to identify which technologies are GENERATION, STORAGE, or TRANSMISSION. Without the MMR entries, those rules will not process MMR’s technologies — they will be invisible to the scenario pipeline even if they pass the capacity investment rule.

4e. Add the firm-capacity fallback row (project input)

Open inputs/execution/firm_capacity_fallbacks_by_cr.xlsx (a project-level input, shared by all profiles), sheet fallbacks. Every country-region needs one row here — it gives the country a firm-capacity allowance for its thermal placeholder technologies (PET/OIL/NGS), used by the reserve-margin repair at solve time. Add the MMR row, identical to every other country’s:

CRTotalAnnualMaxCapacityTotalAnnualMaxCapacityInvestment
MMRXX100.5
What happens without this row

The B2 stage prints warnings like no fallback was provided for CR=MMRXX, prefix=PWRPET and the new country’s thermal placeholders stay capped at 0. When the country then needs firm capacity or peak energy (e.g. during the 2027–2029 transition years), its only escape valve is the backstop at penalty prices — which silently inflates the scenario’s System cost by millions even when the energy shortfall is tiny.

7 Step 5 — Merge into Model Inputs

Merge the generated CSVs into the prepared profile's mutable OSeMOSYS input authority:

python -m ostram --profile unescap country merge MMR

Expected output:

Merged country template: {'TECHNOLOGY': ..., 'FUEL': ..., 'SpecifiedAnnualDemand': ..., 'centerpoint': ...}

The command writes timestamped *.bak.csv siblings before replacing any existing prepared CSV. The committed seed under examples/unescap/inputs/osemosys_global/ remains unchanged.

Tip

All merged CSVs and their backups remain in the ignored prepared workspace. Use inspect-resources to confirm the active osemosys_inputs path before reviewing them.

9 Step 7 — ELC dispatch nodes (nothing to edit)

Each country carries internal ELC dispatch technologies — for Myanmar, ELCMMRXX01. These must be treated as internal fuel-chain nodes, not as standalone power plants; exporting one as a regular technology would make the solver double-count Myanmar’s dispatch capacity.

You do not maintain that list by hand. The scenario stage derives the ELC dispatch nodes from the countries list you edited in Step 4, so adding MMR there is what registers ELCMMRXX01. There is no source file to patch and no list to keep in sync.

Why this step still exists

It used to be a manual edit to a pipeline script, and it was an easy one to forget. It is listed here so you know the behaviour exists and where it comes from — if a new country’s ELC node shows up as a technology in your results, the cause is a missing entry in countries, not a missing edit in the engine.

10 Step 8 — Run A1 + A2 (Create Country Structure)

Run only the base-model and transmission stages now. The skip flags stop before scenario materialisation, compilation, and CBC, leaving the canonical post-A2 snapshots needed by the next step.

python -m ostram --profile unescap run --scenarios "B_Optimised_VRE" --skip-a3 --skip-b1 --skip-b2 --skip-pull
What preparation does

A1 processes the profile’s OSeMOSYS Global CSVs and creates each country’s technology/fuel structure (including ELC fuel codes like ELCMMRXX00–04). A2 adds internal transmission technologies and writes the post-A2 snapshot with the A-O parametrization workbook. Everything lands under <workspace>/preparation/.

Why stop here?

The next step needs the A-O parametrization snapshot that preparation produces. The scenario stage reads the scenario workbook, so the workbook must be populated after preparation and before you run any scenario.

11 Step 9 — Populate the Scenario Workbook

Now that preparation has written the snapshot, populate the profile’s scenario workbook with the new country’s rows. This is what lets the scenario stage find MMR data and apply scenario-specific overrides correctly.

python -m ostram --profile unescap scenario sync-country --country MMR

The command reads the canonical post-A2 BAU snapshot and adds missing MMR rows to the prepared workspace copy of OSTRAM_Scenario_Inputs.xlsx for sheets like Secondary_Techs, Primary_Techs, Demand_Techs, VariableCost, Capacities_CF, and Fixed_Horizon_Parameters. It never edits the committed profile seed, and it is idempotent — running it twice adds nothing the second time.

Tip

Append --dry-run first to see what would be added without modifying the prepared workbook.

What sync-country copies — and what it does not

sync-country reads the A-O parametrization workbook (derived from the OSeMOSYS Global CSVs). It does NOT copy calibrated values from the reference country’s scenario workbook entries. Technologies that have no ResidualCapacity in the CSV will appear with Projection.Mode = EMPTY and empty values — meaning the scenario pipeline will treat them as if they do not exist. The next step adds the missing values.

Quick check of the sync output

The command prints how many rows it added per sheet, all under scenario = BAU (the other scenarios inherit the BAU base). Confirm Primary_Techs got the MIN*MMR rows (e.g. MINCOAMMR) and Secondary_Techs the PWR*MMRXX rows. Zero MMR rows in a sheet means Step 8’s A1+A2 run did not complete.

Demand profile — nothing to edit

You do not need to add Myanmar rows to the Demand_Profiles sheet by hand. The scenario stage detects every region configured in the countries list and generates the ELCMMRXX03 demand-profile rows automatically from the MMR_Dem timeslice sheet that Step 2 cloned. Look for the line + Added demand entity ELCMMRXX03 ... in the run log of Step 11.

12 Step 10 — Calibrate the Scenario Workbook Critical

Why this step is required

Stage 1b marks a technology ALLOWED only if it has ResidualCapacity > 0 or TotalAnnualMinCapacityInvestment > 0 in some year; everything else is ZEROED (max capacity 0, nothing can be built). Without this calibration Myanmar would only have coal, hydro, oil and solar PV.

Open the prepared workspace copy of OSTRAM_Scenario_Inputs.xlsx (the one under <workspace>/profiles/unescap/authorities/scenario_workbook/) and go to the Secondary_Techs sheet. Find the MMR rows for the technologies listed below.

After Step 9 the MMR rows arrive in two states, so this step has two small tasks — A: overwrite the values of 2 rows that already came filled, and B: fill in 6 rows that came empty. 8 rows in total, all in Secondary_Techs, all with scenario = BAU.

Calibration for this training exercise (realistic Myanmar)

Why these values

With demand_scale: 0.18 Myanmar’s demand is realistic (~90 → ~319 PJ). The cloned CSVs already give oil 2.56 GW, coal 0.25 and solar 0.17; this step adds hydro (Myanmar’s backbone) plus small wind/biomass/nuclear entries — ~6.5 GW total, enough to keep the backstop at zero. Do not copy Bangladesh’s full 25 GW fleet: it is not needed, and it makes the solver grind for hours.

Training values — in a real project you would replace them with actual Myanmar statistics:

A — Overwrite the year values (2 rows, both hydro)

These two rows already arrived with Projection.Mode = User defined and Bangladesh’s cloned numbers. Do not touch the mode — just replace the value in every year column:

TechnologyParameterCloned value (today)New value (all years)
PWRHYDMMRXX (Hydro) ResidualCapacity 0.23 3.5
PWRHYDMMRXX (Hydro) TotalAnnualMaxCapacity 0.8302 40
Why both hydro rows are mandatory

3.5 GW is Myanmar’s real hydro fleet. The 40 is not optional: the cloned ceiling (0.8302, Bangladesh’s hydro potential) is below the new 3.5 residual, and the model refuses to run whenever ResidualCapacity exceeds TotalAnnualMaxCapacity — the run aborts with GLPK check[GLOBAL,PWRHYDMMRXX,2023] failed. 40 GW is the order of Myanmar’s technical hydro potential.

B — Fill the empty rows (6 rows)

These rows arrived with Projection.Mode = EMPTY and no values. For each one: set Projection.Mode = User defined, set Projection.Parameter = 0, and fill every year column — most years are 0, except the single year shown:

TechnologyParameterValues
PWRWONMMRXX (Onshore Wind) ResidualCapacity 0.063 in all years
PWRBIOMMRXX (Biomass) ResidualCapacity 0.001 in all years
PWRHYDMMRXX (Hydro) TotalAnnualMinCapacityInvestment 0 in all years, except 2025 = 0.5
PWRSPVMMRXX (Solar PV) TotalAnnualMinCapacityInvestment 0 in all years, except 2027 = 0.3
PWRWONMMRXX (Onshore Wind) TotalAnnualMinCapacityInvestment 0 in all years, except 2035 = 0.2
PWRURNMMRXX (Nuclear) TotalAnnualMinCapacityInvestment 0 in all years, except 2030 = 0.11
Two easy mistakes to avoid

Solar: the row you fill is SPV’s TotalAnnualMinCapacityInvestment; its ResidualCapacity row (0.17, already filled) is a different row — leave it alone. Nuclear: use 0.11 in 2030 only (an SMR pilot) — do not copy Bangladesh’s 1.2, and never put a value in every year, or the model is forced to over-build nuclear.

Leave as cloned — verify only

PWROILMMRXX (2.56 GW), PWRCOAMMRXX (0.25) and PWRSPVMMRXX (0.17) already carry residual capacity — just confirm the values are there. Their decline over the years (oil → 0.481 by 2035, coal → 0 by 2030) is the cloned retirement trajectory and is expected.

Check after running

After Step 11, verify the backstop stayed (near) zero: in the results, PWRBCKMMRXX should have essentially no generation, and the dashboard’s System cost should be in the same order of magnitude as before the country was added. A large backstop contribution means demand is still outrunning the calibrated fleet.

How to find the rows

In Secondary_Techs, search the Tech column for PWRWONMMRXX / PWRBIOMMRXX / PWRURNMMRXX with Parameter = ResidualCapacity or TotalAnnualMinCapacityInvestment. MMR rows exist only under scenario = BAU; the other scenarios inherit them. If you find MMR rows tagged with a non-BAU scenario, delete them — they would silently shadow your calibration.

Do not skip this step

Without these values, the capacity investment rule will block wind, biomass, and nuclear for Myanmar. The model will still solve (it is not infeasible), but Myanmar’s generation mix will be limited to only four technologies: coal, hydro, oil, and solar PV.

Why Bangladesh works without this step

The profile’s seed scenario workbook already ships with calibrated values for Bangladesh — for example, PWRWONBGDXX has ResidualCapacity = 0.063. These were added by the model builders and are part of the committed profile data. When you add a new country, the template generator and sync-country only copy CSV-derived data, not these calibrated workbook entries. This step fills that gap for MMR.

13 Step 11 — Run the Scenarios

Now that the scenario workbook has MMR’s data, run the scenarios. The run reuses the preparation output already in the workspace and goes straight to the scenario, compilation, and execution stages.

Run scenarios A and B:

python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU,B_Optimised_VRE"

Run scenario C (its completed-A dependency is declared in config/scenarios/registry.json, so it runs separately — and running it before A stops with a clear message):

python -m ostram --profile unescap run --scenarios "C_Target_VRE"
What happens now

A3 reads the scenario workbook (now with MMR rows) and materialises scenario overrides into the A-O workbooks. B1 compiles everything into solver-ready input files. B2 runs the solver — this profile is configured for CBC. Confirm OPTIMAL SOLUTION FOUND for all scenarios.

Expected runtime

The scenario, compilation, and execution stages together typically take 15–30 minutes depending on your machine and solver.

14 What’s Next?

Myanmar is now in the model with generation data and calibrated technologies, but it is electrically isolated — there are no interconnectors connecting it to neighbouring countries.

  • To connect Myanmar to its neighbours, add interconnectors (see Exercise B: Add a New Transmission Interconnector).
  • For a real project: replace the cloned and training-calibration values with actual data from IRENA, national statistics, or IEA, then parametrise the model fully. The calibration in Step 10 used Bangladesh’s values as placeholders — real residual capacities and investment limits will differ.
Important distinction

This process is for countries NOT in OSeMOSYS Global. Countries that ARE already in OSeMOSYS Global follow a different, longer process that requires Linux or WSL. The template generator is a shortcut for countries outside the OSeMOSYS Global dataset.

15 Troubleshooting

ProblemCauseSolution
Script says country already exists The template folder already has data for this country. Run python -m ostram --profile unescap country template again; each run rewrites its own workspace template files, so there is nothing to delete by hand.
Validation shows FAIL One or more of the three YAML sections is missing the MMR entry. Check that country_data, countries, and implausible_combinations are all updated in examples/unescap/config/preparation/Config_country_codes.yaml.
ModuleNotFoundError Missing Python dependencies. Make sure you are in the environment where OSTRAM is installed (python -m ostram --help should work).
Unknown profile: unescap The installed OSTRAM build does not contain the UNESCAP profile, or the project root is wrong. Run from this integrated repository or install a build that includes examples/unescap/profile.yaml.

Solver infeasible after adding country Missing demand or capacity data for MMR. Check that the merge succeeded. Verify that the prepared osemosys_inputs/SpecifiedAnnualDemand.csv reported by inspect-resources has MMR rows.

Run python -m ostram --profile unescap country template again (it re-clones the sheets into the workspace copy), verify MMR_CF/MMR_Dem exist (see the check in Step 2), then re-run. Remember that example prepare --reset discards the workspace copy, including these sheets.
Myanmar shows demand but a flat or missing demand profile in results The scenario stage generates ELCMMRXX03 demand-profile rows automatically from the MMR_Dem sheet. If MMR_Dem was cloned from Bangladesh and never replaced, Myanmar simply reuses Bangladesh’s profile shape — expected for this training exercise. Confirm the Step 11 run log prints + Added demand entity ELCMMRXX03. For a real project, replace the cloned MMR_Dem values with Myanmar’s actual demand profile.

1 The Training Model

The full OSTRAM model covers six South-Asian countries (Bangladesh, Bhutan, India — in five regions —, Nepal, Sri Lanka and the Maldives). That model is large and slow to solve, which makes it awkward for learning. For training we use a reduced two-region model — Bangladesh plus the Indian region it actually trades power with:

Bangladesh BGDXX

A large, fossil-heavy system: natural gas dominates, alongside coal, oil and fast-growing solar. Rich enough to show real trade-offs between technologies.

India – East INDEA

India's Eastern region (West Bengal, Bihar, Jharkhand, Odisha) — a coal-heavy grid with hydro and emerging renewables, and a large neighbour to import from and export to.

The two regions are joined by a real cross-border interconnector, TRNBGDXXINDEA — the Bangladesh–India HVDC link (Bheramara–Baharampur plus its planned expansions, growing from ~2.5 GW today toward 8.5 GW). Everything else (the other four Indian regions, Bhutan, Nepal, Sri Lanka and the Maldives) has been removed from the input data, so runs are fast and the results are easy to read.

Think of it this way

The reduced model is a flight simulator. It behaves like the real OSTRAM model — same scripts, same scenario logic, same output files — but it is small enough that you can take off, try something, and land again in minutes.

Region codes you will use

Throughout the exercises, Bangladesh is BGDXX and India East is INDEA. Technology names embed these codes, e.g. PWRSPVBGDXX (Bangladesh solar PV) or PWRSDSINDEA (India-East short-duration storage).

2 How Scenarios Are Built

OSTRAM always starts from one shared baseline and branches into scenarios from there. You never edit the raw model by hand — you change a small configuration file, and the pipeline rebuilds the scenario for you.

The pipeline stages

StageWhat it does
A1 + A2Read the input CSVs and build the BAU snapshot — the common starting point for every scenario. Runs once; the snapshot is then reused.
A3For each scenario, restore the BAU snapshot and apply that scenario's rules (driven by its YAML config files). This is the stage you steer in these exercises.
B1Compile every scenario's data into a solver-ready dataset.
B2Run the optimiser and write the results.

The three scenarios

ScenarioIdeaMain YAML lever
A_Calibrated_BAUBusiness-as-usual, locked to today's technology mix. The calibrated baseline every other scenario is measured against.lid_rule.yaml
B_Optimised_VRELet the optimiser build renewables aggressively; nudge storage in early.lid_rule.yaml + storage_floors.yaml
C_Target_VREImpose renewable-energy targets as hard constraints (NDC-style policy goals).set_vre_targets.yaml

All three configs live under:

examples/unescap/config/scenarios/<SCENARIO>/

That is the unescap profile — one self-contained example under examples/unescap/ holding its own inputs, configs, scenario registry, and docs. Every command names the profile (--profile unescap) rather than a directory, so nothing depends on where you are standing when you run it.

Think of it this way

The BAU snapshot is the base recipe. Each scenario is the same recipe with a few ingredients adjusted — and the YAML file is your shopping list of adjustments.

3 Before You Start: First Build

Build the baseline results once, in two passes. This order matters: C_Target_VRE scales its targets against the solved A_Calibrated_BAU results, so the calibrated baseline must be solved before the policy scenario runs.

Step 0 — Get a conda terminal

All commands below run from a terminal with conda available — an Anaconda Prompt on Windows, or your normal Terminal on macOS and Linux with the conda environment activated. If you don't have conda, install either Anaconda Distribution or the lighter Miniconda. Both give you a working conda command line.

  1. Check that OSTRAM is installed. There is no training branch to check out and no folder to navigate to — the UNESCAP model ships inside OSTRAM as the unescap example profile. Confirm the command is on your path: 
    python -m ostram --help
  2. Prepare the profile. The profile ships input CSVs and a scenario workbook, not a built model, so preparation must run once before any scenario can be compiled or solved. Repeat it only after you change country membership. 
    python -m ostram example prepare unescap
  3. Pass 1 — build & solve the calibrated baseline and the VRE scenario. This builds the snapshot (if needed) and produces the solved A_Calibrated_BAU results that the next pass relies on: 
    python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU,B_Optimised_VRE"
  4. Pass 2 — run the policy scenario. It now finds the solved CalBAU results and builds its renewable-target floors on top of them: 
    python -m ostram --profile unescap run --scenarios "C_Target_VRE"
  5. Save your baseline snapshot. Every run replaces the current combined results, and they only hold the scenarios you have solved so far. So you can compare later, record this run under a label — the results dashboard (Section 8) lists every recorded <LABEL> in its Before/After menus: 
    python -m ostram example report unescap --capture baseline

    The label baseline marks this as your untouched, pre-exercise starting point. The command stamps the date for you.

Why two passes?

A single run builds every requested scenario (the A3 stage) before it solves any of them (the B2 stage). So in a single all-scenarios run, C_Target_VRE is built while A_Calibrated_BAU is still unsolved — and it aborts with "BAU results not found… Run the BAU/CalBAU scenario first." Solving A first (pass 1) fixes this.

If you change the input data

Preparation output is reused on every run. If you edit the raw model under examples/unescap/inputs/osemosys_global/, prepare the profile again so the base model is rebuilt from your new data:

python -m ostram example prepare unescap --rebuild

Nothing needs deleting by hand. Preparation owns its workspace and replaces stale output itself; no generated folder lives inside the profile.

Save your baseline numbers

After the first build, note a few headline figures for each scenario (total system cost, total CO₂ emissions, and the 2050 generation mix). Every exercise asks you to compare against these baseline values. To re-run a single scenario after editing its YAML, use python -m ostram --profile unescap run --scenarios "<name>".

4 Exercise 1: The Investment Lid A_Calibrated_BAU

Goal

Understand how the investment lid keeps the calibrated baseline anchored to today's technology mix — and watch what happens when you loosen it.

The concept

Each year the model is allowed to build only so much new capacity of each technology. That cap is the lid (TotalAnnualMaxCapacityInvestment). In A_Calibrated_BAU the lid is locked: the future build-out is forced to follow the same proportions as 2023, so the scenario reproduces a credible "nothing changes" baseline.

Think of it this way

The lid is a monthly spending limit per category. A relaxation_schedule of 1.0 everywhere means "spend exactly like last year." Raising it to 2.0 by 2050 means "you may build up to twice as much new capacity as the baseline allows."

The file to edit

examples/unescap/config/scenarios/A_Calibrated_BAU/lid_rule.yaml

What to change

Find the relaxation_schedule block. By default it is flat at 1.0 (locked). Replace it so the lid gradually opens up — allowing 50% more build by 2030 and double by 2050:

Before (locked)

relaxation_schedule:
  2023: 1.0
  2050: 1.0

After (loosened)

relaxation_schedule:
  2023: 1.0
    2030: 1.5
  2050: 2.0

Optionally, also raise the per-technology minimum build from 0.5 GW to see more new capacity seeded each year:

lid_floor_gw: 1.0   # was 0.5

Run it

python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU"

Then save this run under an exercise label and open the dashboard to compare it against your baseline:

python -m ostram example report unescap --capture E1

In the dashboard set Before = baseline, After = E1, Scenario = A_Calibrated_BAU, and switch Region between System, Bangladesh and India-East to watch the lid open up. (See Section 8 for details.)

What to observe

  • More new solar and wind capacity built in Bangladesh and India East toward 2050, compared with your locked baseline.
  • A shift in the 2050 generation mix — cheaper technologies expand once the lid lets them.
  • A change in total system cost: with more freedom to invest, the optimiser usually finds a lower operating cost (at the price of more up-front capacity).
Remember to revert

A_Calibrated_BAU is a calibration — its job is to match observed 2023 behaviour. Loosening the lid is a learning experiment, not a real baseline. When you are done, restore the original values (see Section 8).

5 Exercise 2: Ceilings & Storage B_Optimised_VRE

Goal

Steer an aggressive renewables scenario by (a) phasing down a fossil family with a family ceiling, and (b) seeding batteries with a storage floor.

The concept

B_Optimised_VRE already lets renewables grow fast (its lid relaxes up to 25× by 2050). Two finer controls shape how that growth happens:

  • Family ceilings cap the relaxation for a specific fuel family. A ceiling of 1.0 locks a family to baseline proportions; below 1.0 forces it to shrink.
  • Storage floors set a small guaranteed amount of new battery / long-duration storage each year, so the optimiser starts deploying storage early instead of waiting.

Part A — Phase down coal

Edit:

examples/unescap/config/scenarios/B_Optimised_VRE/lid_rule.yaml

In family_relaxation_ceilings, push coal below its baseline so the coal fleets of Bangladesh and coal-heavy East India are forced to retire faster — and squeeze natural gas (Bangladesh's dominant fuel) at the same time:

Before

family_relaxation_ceilings:
  COA: 1.0
  NGS: 1.2
  # ...

After

family_relaxation_ceilings:
  COA: 0.5   # shrink coal
  NGS: 0.8   # squeeze gas
  # ...

Part B — Seed more storage

Edit:

examples/unescap/config/scenarios/B_Optimised_VRE/storage_floors.yaml

Triple the early short-duration (battery) floor so storage shows up sooner alongside the new solar:

Before

storage_floors:
  SDS:
    2029: 0.05
    2030: 0.10
    # ...

After

storage_floors:
  SDS:
    2029: 0.15
    2030: 0.30
    # ...

Run it

python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"

Then save this run and open the dashboard to compare it against your baseline:

python -m ostram example report unescap --capture E1+E2

In the dashboard set Before = E1, After = E1+E2, Scenario = B_Optimised_VRE. Because runs are cumulative, the previous exercise's snapshot (E1) is the fair “before” here — so the coal/gas ceilings and the storage floor show up cleanly in the generation mix, CO₂ line and storage chart. (See Section 8.)

What to observe

Change you madeExpected effect
COA: 0.5Coal generation in Bangladesh and East India falls below baseline; CO₂ emissions drop; solar and gas fill the gap.
NGS: 0.8Natural gas (Bangladesh's dominant fuel) is squeezed too, pushing the mix further toward solar.
SDS floors upEarlier and larger battery deployment in both regions, smoothing solar output.
Experiment

Try the two parts separately first (coal ceiling alone, then storage floor alone) so you can attribute each effect. Then combine them and see how they interact.

6 Exercise 3: Interconnectors — On & Off

A focused set of exercises on the Bangladesh–India cross-border power link. Switch the interconnector off, open it wide, reshape its build-out, find the sweet spot, and control its direction — each by editing a single YAML file.

The Cross-Border Link

These exercises use the same reduced two-region training model as the main guide: Bangladesh (BGDXX) and India's Eastern region (INDEA). The one thing that ties them together is a single real interconnector — the Bangladesh–India HVDC link:

TRNBGDXXINDEA   # Bheramara–Baharampur HVDC + planned expansions

It is the corridor that lets the two grids share power. Today it carries about 2.5 GW; the real project pipeline grows it toward 8.5 GW by 2033. In the reduced model it is the only interconnector, which makes it perfect for a clean on/off experiment: whatever you do to it, you see the effect immediately in how the two regions lean on — or fend for — each other.

Exact baseline versus exercise edits

The shipped workbook and every executable scenario anchor retain ResidualCapacity = 2.496 GW for 2023–2028. This guide uses “2.5 GW” only as rounded prose. Typing an exact 2.500 value is an exercise edit, not a baseline correction.

Think of it this way

The interconnector is an extension cord between two houses. Unplug it and each house must generate everything it needs on its own. Plug in a fatter cord and the house with cheap solar at noon can sell it next door instead of curtailing it — and borrow power back after sunset.

Codes you will use

Bangladesh is BGDXX, India East is INDEA, and the link between them is TRNBGDXXINDEA. Interconnector technologies always start with TRN and are 13 characters long (source region + destination region).

The Lever: relax_interconnectors.yaml

Every scenario has its own copy of one small config file that decides how much the interconnector may grow. That single file is the switch you will flip in all four exercises:

examples/unescap/config/scenarios/<SCENARIO>/relax_interconnectors.yaml

Here is the default (the real project pipeline used by B_Optimised_VRE):

mode: multiplicative
headroom_factor: 1.5          # default slack for links without an override

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2028: 6.50, 2029: 7.00, 2030: 7.75, 2033: 8.50}

Two things control the link:

SettingWhat it does
overridesAn absolute cap in GW on new interconnector capacity, staged by year. Values between years are interpolated linearly and held flat after the last year. This is the precise switch — it also lifts the total-capacity ceiling so the link can actually be built.
mode + headroom_factor / headroom_gwThe fallback for any link without an override: multiplicative (ResidualCapacity × factor), additive (ResidualCapacity + GW) or unconstrained (no cap).
Why we steer with the override

The base model freezes each interconnector at its existing capacity (TotalAnnualMaxCapacity = ResidualCapacity). Giving TRNBGDXXINDEA an override with any non-zero value is what tells OSTRAM to lift that ceiling and let new capacity be built. So the override is both the amount and the on-switch — that is why every exercise here edits it directly.

One safety floor to know

An override can never push capacity below the link's ResidualCapacity (today's real ~2.5 GW) — the script clamps it up if you try. So “off” in these exercises means frozen at today's link, no expansion, not a physical disconnection. To model a full outage you would zero the interconnector's ResidualCapacity in the raw input data instead.

3.1 Exercise 3.1: Switch It Off B_Optimised_VRE

Goal

Freeze the interconnector at today's capacity so no new cross-border capacity is ever built, and watch each region cope on its own.

The concept

In the default config the link grows from 2.5 GW to 8.5 GW. To turn expansion off, remove the override entirely (leave overrides: empty as {}) and set the fallback factor to 1.0. With no override the base model's freeze is left untouched — it already pins the link's total capacity to today's 2.5 GW — so the two grids keep the wire they already have, but cannot add to it: each region must meet its own demand growth with its own generation.

The file to edit

examples/unescap/config/scenarios/B_Optimised_VRE/relax_interconnectors.yaml

What to change

Before (pipeline, growing)

headroom_factor: 1.5

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2028: 6.50,
                  2029: 7.00, 2030: 7.75,
                  2033: 8.50}

After (frozen — off)

headroom_factor: 1.0

overrides: {}   # no override -> base 2.5 GW freeze holds
Why empty — and not a flat 2.496 override

The base model already freezes the link by pinning TotalAnnualMaxCapacity = ResidualCapacity (exactly 2.496 GW). The relax script reads any non-zero override — even a flat {2023: 2.496, 2050: 2.496} — as “open this link”: it lifts that total-capacity ceiling to 9999 and then caps only the annual build rate. The corridor is then free to grow (it climbed to ~10 GW). An override can cap investment; it can never pin total capacity. So the way to freeze is to add no override and let the base 2.496 GW ceiling stand.

Run it

python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"

Then save this run under an exercise label and open the dashboard:

python -m ostram example report unescap --capture IC-off

In the dashboard set Before = baseline, After = IC-off, Scenario = B_Optimised_VRE, and switch Region between System, Bangladesh and India-East.

What to observe

  • Interconnector capacity stays flat at 2.5 GW across the whole horizon — the pipeline is gone.
  • The importing region (India East) builds more of its own capacity to stay reliable without imports; the exporting region (Bangladesh) may build less because it no longer needs to serve cross-border demand. The generation mixes drift apart.
  • System cost usually rises and any shared-VRE benefit shrinks — without a bigger wire, cheap solar in one region can't relieve the other.
“Off” means frozen, not disconnected

The existing 2.5 GW line cannot be removed through this file (it is protected by the ResidualCapacity floor). This exercise switches off growth. That is the honest “no new interconnection” policy question most planners actually face.

3.2 Exercise 3.2: Open It Wide B_Optimised_VRE

Goal

Do the opposite of Exercise 1: give the optimiser far more interconnection than the real pipeline and let it build as much trade capacity as it finds economic.

The concept

Raise the override well above the 8.5 GW pipeline — say up to 25 GW by 2050. Because the override is now a generous ceiling rather than a binding cap, the optimiser will build interconnection only up to the point where extra trade still pays for itself. This shows the economic appetite for cross-border capacity.

What to change

Before (real pipeline)

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2028: 6.50,
                  2029: 7.00, 2030: 7.75,
                  2033: 8.50}

After (wide open)

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2030: 15.0, 2050: 25.0}
Why this is the true “on” switch

A non-zero override lifts the total-capacity ceiling, so the corridor is free to grow. Leave headroom_factor as it is — it only affects links that have no override, and this is the only link.

Run it & compare

python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"
python -m ostram example report unescap --capture IC-wide

Set Before = baseline (or IC-off for the sharpest contrast) and After = IC-wide.

What to observe

  • Interconnector capacity climbs above the 8.5 GW pipeline — but only as far as the optimiser judges worthwhile, which tells you how much trade the system actually wants.
  • More solar built in the cheaper region and exported next door; less curtailment of midday VRE.
  • System cost usually falls versus the frozen case — a shared grid is cheaper than two self-sufficient ones.

3.3 Exercise 3.3: Reshape the Ramp B_Optimised_VRE

Goal

Keep the same 8.5 GW destination but change when the capacity arrives — testing how sensitive the results are to build timing rather than final size.

The concept

The override is a schedule, so you can shift the whole ramp earlier or later. Run it once fast and once slow and compare — the endpoint is identical, only the path differs.

What to change

Variant A — early (full link by 2026)

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2026: 8.50}

Variant B — late (full link only by 2045)

overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2045: 8.50}

Run each variant on its own, saving a distinct label so you can line them up in the dashboard:

# after editing to Variant A
python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"
python -m ostram example report unescap --capture IC-early
# then edit to Variant B, re-run, and record it as --capture IC-late

What to observe

  • The early link lets high-VRE trade start sooner, so solar ramps up earlier in both regions.
  • The late link delays those gains — more domestic fossil generation in the interim, and often higher cumulative CO₂.
  • By 2050 the two variants converge, which shows the cost of waiting is paid mostly in the transition years.
Single-variable discipline

Because Variants A and B share the same 8.5 GW endpoint, any difference you see is caused purely by timing — a clean way to isolate one effect.

3.4 Exercise 3.4: Find the Sweet Spot B_Optimised_VRE

Goal

Sweep the final link size to find where extra interconnection stops paying off — the point of diminishing returns.

The concept

Exercises 1 and 2 gave you the two extremes (frozen vs. wide open). Now fill in the middle. Re-run the scenario a few times, each with a different 2050 ceiling, and plot system cost against link size. Somewhere between “off” and “wide open” the curve flattens — that knee is the economically efficient interconnector size.

What to change

Run the scenario once per row below, editing only the override and saving a matching label:

Override for TRNBGDXXINDEASave as label
{2023: 2.496, 2050: 2.496}IC-2.496 (= off)
{2023: 2.496, 2033: 5.00}IC-5
{2023: 2.496, 2033: 8.50}IC-8.5 (= pipeline)
{2023: 2.496, 2033: 12.0}IC-12
{2023: 2.496, 2030: 15.0, 2050: 25.0}IC-25 (= wide)
 
# repeat for each row: edit the override, then
python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"
python -m ostram example report unescap --capture IC-8.5

What to observe

  • System cost drops steeply as the link grows from 2.5 GW, then flattens — the knee of the curve is the sweet spot.
  • Trade flows and shared VRE keep rising with capacity, but the marginal benefit of each extra GW shrinks.
  • Beyond a point the line is barely used at full size — a sign the corridor is oversized for this system.
Make it a chart

Enter each run's system-cost KPI into a small table (link size vs. cost) and plot it. That single curve is exactly how planners justify an interconnector's size to a ministry.

3.5 Exercise 3.5: Control the Direction B_Optimised_VRE

Goal

Force the interconnector to carry power in one direction only and compare the results against the default bidirectional flow — revealing which region is the natural exporter and how much value comes from allowing trade in both directions.

The concept

The interconnector TRNBGDXXINDEA has two modes of operation. Mode 1 moves power from Bangladesh to India East; mode 2 moves it the other way. In the default (bidirectional) configuration both modes are active and the optimizer chooses the flow direction each year. By disabling one mode you can test what happens when only one country is allowed to export.

Think of it this way

Imagine the extension cord between two houses can carry power in both directions. Normally, whichever house has surplus at a given hour pushes it to the other. Now picture a one-way valve on the cord — only one house can ever send. That changes who builds what generation, because the blocked house can never lean on its neighbour for exports.

The lever: set_interconnector_direction.yaml

This exercise uses a second config file, separate from relax_interconnectors.yaml:

examples/unescap/config/scenarios/B_Optimised_VRE/set_interconnector_direction.yaml

It has one key, directions, mapping each interconnector to a direction:

ValueWhat it does
forwardKeep only mode 1 (BGD → INDEA). The reverse mode is disabled by zeroing its InputActivityRatio and OutputActivityRatio.
reverseKeep only mode 2 (INDEA → BGD). The forward mode is disabled.
bidirectionalNo-op — both modes stay active. Same as omitting the entry entirely.
How forward / reverse is determined

The script parses the technology name TRNBGDXXINDEA to identify the source and destination regions, then matches each mode's input fuel to a region. The mode whose input fuel contains the source region (BGDXX) is the forward mode; the other is reverse. This works automatically for any interconnector that follows the TRN<SRC><DST> naming convention.

What to change

You will run the model three times, saving a labelled snapshot after each:

Run 1 — forward only

directions:
  TRNBGDXXINDEA: forward   # BGD -> INDEA only

Run 2 — reverse only

directions:
  TRNBGDXXINDEA: reverse   # INDEA -> BGD only

Run 3 is the bidirectional default — set directions: {} (or remove the entry) and re-run.

Keep relax_interconnectors.yaml unchanged

This exercise only edits the direction file. Leave relax_interconnectors.yaml at the default pipeline so the capacity ceiling is the same across all three runs. The direction script controls which way the wire carries power; the relax script controls how much wire is built.

Run it

For each direction, run the scenario once. The run restores clean inputs from the BAU snapshot, applies the direction rule, then compiles and solves:

# 1. Edit set_interconnector_direction.yaml to "forward"

# 2. Run the scenario
python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"

# 3. Record it under a direction label
python -m ostram example report unescap --capture forward

# 4. Repeat for "reverse" and "bidirectional", recording --capture reverse and --capture bidirectional

Generate the comparison report

Once you have all three labelled runs, build the comparison report — a self-contained HTML page with interactive charts:

python -m ostram example report unescap --compare forward,reverse,bidirectional

The report is written into your workspace. Open it in a browser to see the side-by-side charts.

What to observe

  • Reverse dominates. India East is the natural exporter — it has a much larger power system. The reverse-only solve builds up to ~12.7 GW and pushes 383 PJ at peak. Forward-only stays at 2.5 GW with very low production.
  • Bidirectional is the sweet spot. The optimizer uses mode 2 (INDEA→BGD) in the early years, then switches to mode 1 (BGD→INDEA) from 2040 onward as Bangladesh's renewables mature. Capacity settles at ~10.3 GW — between the two extremes.
  • Forward-only is expensive. Bangladesh has little surplus to export, so the link sits nearly idle and each region must build more of its own capacity.
  • Direction matters for policy. A one-way agreement (e.g. “India sells to Bangladesh but not vice versa”) yields a very different build-out than a mutual trade agreement. This exercise quantifies that difference.
Example YAML files included

The profile ships ready-made example configs in examples/unescap/config/scenarios/B_Optimised_VRE/: set_interconnector_direction_EXAMPLE_forward.yaml and set_interconnector_direction_EXAMPLE_reverse.yaml. Copy either one over set_interconnector_direction.yaml to use it.

Pre-built results

A ready-made comparison report with interactive charts from an earlier three-way solve ships with the profile (interconnector direction results):

# Open the pre-built results in your browser:
examples/unescap/references/interconnector-direction-results.html

This report shows installed capacity, mode activity, and total production side by side for all three configurations, with summary metrics and a step-by-step guide for reproducing the comparison yourself.

Inspecting Results & Reverting

Where to look

After each run the combined results land in the execution workspace, and the dashboard reads every recorded label. For interconnector exercises the most telling views are capacity (watch the TRNBGDXXINDEA line move), generation mix per region, CO₂ emissions and system cost.

python -m ostram example report unescap

Undoing your changes

To put the corridor back the way it shipped, restore the two lines the profile defines for it in examples/unescap/config/scenarios/B_Optimised_VRE/relax_interconnectors.yaml:

headroom_factor: 1.5
overrides:
  TRNBGDXXINDEA: {2023: 2.496, 2028: 6.50, 2029: 7.00, 2030: 7.75, 2033: 8.50}

And for the direction file (Exercise 3.5), the shipped default is bidirectional:

directions: {}

Then re-run the scenario to rebuild clean results:

python -m ostram --profile unescap run --scenarios "B_Optimised_VRE"
Good habit

Change one value at a time, run, and write down what moved. Keeping the baseline snapshot untouched means you can always measure the total effect of any experiment.

7 Exercise 4: Renewable Targets C_Target_VRE

Goal

Impose a renewable-energy target as a hard constraint and see how the model is forced to meet it — and what it costs.

The concept

Exercises 1 and 2 changed what the model is allowed to do. C_Target_VRE changes what it must do: each target sets a minimum share of a region's generation that a technology has to deliver by a given year (an NDC-style policy floor). The optimiser then has no choice but to build enough to comply.

Think of it this way

A ceiling says "you may spend up to this much." A target is the opposite — "you must reach at least this much." If the goal is set too high to be physically reachable, the model has no feasible answer at all.

The file to edit

examples/unescap/config/scenarios/C_Target_VRE/set_vre_targets.yaml

The targets list holds one row per region and technology. Each schedule maps a year to a target share of that region's total generation. For the reduced model there are two rows — one for India East, one for Bangladesh:

targets:
  # India East: a token solar floor (coal-heavy region, very low solar today)
  - {cr: INDEA, tech: "PWRSPV*", schedule: {2023: 0.006, 2027: 0.006, 2030: 0.015, 2050: 0.015}, cap_envelope: true}
  # Bangladesh: solar share rising to 20% by 2050
  - {cr: BGDXX, tech: "PWRSPV*", schedule: {2023: 0.011, 2027: 0.011, 2030: 0.064, 2050: 0.200}, cap_envelope: true}

What to change

Make Bangladesh more ambitious — raise its 2050 solar share from 0.200 to 0.350 — and lift coal-heavy India East from a token 0.015 to 0.050 by 2050:

  - {cr: INDEA, tech: "PWRSPV*", schedule: {2023: 0.006, 2027: 0.006, 2030: 0.015, 2050: 0.050}, cap_envelope: true}
  - {cr: BGDXX, tech: "PWRSPV*", schedule: {2023: 0.011, 2027: 0.011, 2030: 0.064, 2050: 0.350}, cap_envelope: true}
Needs a solved baseline

This scenario reads the solved A_Calibrated_BAU results. If you have not solved CalBAU since your last clean rebuild, run it first: python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU". Otherwise you will see "BAU results not found".

Run it

python -m ostram --profile unescap run --scenarios "C_Target_VRE"

Then save this run and open the dashboard to compare it against your baseline:

python -m ostram example report unescap --capture E1+E2+E3

In the dashboard set Before = E1+E2, After = E1+E2+E3, Scenario = C_Target_VRE — E1+E2 is the cumulative state just before this exercise. Watch the solar/VRE-share line rise to meet the target. Capital investment rises (more solar capacity to build), but total discounted system cost may actually fall because solar’s zero fuel cost offsets the higher capex. (See Section 8.)

What to observe

  • Solar generation in both regions is pulled up to exactly meet the new floors — the target binds.
  • More solar capacity (and supporting storage) is built earlier than the model would choose on its own.
  • Capital investment rises (more solar panels to build), but total discounted system cost may fall — solar’s zero fuel cost can more than offset the higher capex, making the forced target cheaper overall.
Feasibility

Targets are hard constraints. If you set a share the system physically cannot reach (e.g. a solar share far above what the grid and storage can absorb), the solver will report the model as infeasible and produce no result. If that happens, lower the target, raise it more gradually across years, or revert. Pushing a target to the edge of feasibility is itself a valuable lesson.

8 Inspecting Results & Reverting

Where the results land

After a run, each scenario's solver output is written under its own folder in the execution workspace, alongside the combined input/output tables. Nothing is written inside examples/unescap/:

<workspace>/execution/Executables/<SCENARIO>_0/   # per-scenario solver outputs
<workspace>/execution/OSTRAM_Outputs.csv          # model results
<workspace>/execution/OSTRAM_Combined_Inputs_Outputs.csv

Two useful result tables to open are ProductionByTechnology (generation per technology and year) and the capacity tables — that is where you will see your edits show up. python -m ostram example report unescap reads these outputs for you and builds the comparison dashboard.

Comparing scenarios

To rebuild several scenarios at once for a side-by-side comparison, pass them together:

python -m ostram --profile unescap run --scenarios "A_Calibrated_BAU,B_Optimised_VRE,C_Target_VRE"

Visualise before vs after

To see what your edits changed, generate the interactive results dashboard. Every run you recorded with --capture becomes a selectable point in the dashboard's Before and After menus, listed by its label:

python -m ostram example report unescap

This writes the dashboard into your workspace. Open it in a browser and pick a Before snapshot, an After snapshot, a scenario (A/B/C) and a region (System / Bangladesh / India-East) to compare generation mix, capacity, CO₂ emissions, storage, renewable share and system cost side by side.

Keep a baseline, label every run

Each run replaces the current combined results, and those results only hold the scenarios you have solved so far — so record a label after every build. Right after the first build use --capture baseline; after Exercise 1 --capture E1, after Exercise 2 --capture "E1+E2", after Exercise 3 --capture "E1+E2+E3". Runs are cumulative (each carries the previous exercises' edits), so compare a run against the previous snapshot to isolate one exercise (e.g. E1 vs E1+E2), or against baseline to see the total change since the start.

Undoing your changes

Every config file in the profile is small, commented, and carries its shipped values in its own header, so the safest way back is to put the original numbers in and save. Each exercise above quotes the value it asks you to change, so you always have the “before” in front of you.

The profile is also version-controlled, so your editor's file history and your version-control client both show exactly which lines you changed — use whichever you are comfortable with to revert. Nothing you generate lives inside examples/unescap/, so a revert never destroys results.

Good habit

Change one parameter at a time, run, and write down what moved. That single-variable discipline is exactly how energy modellers isolate the effect of a policy or assumption.
